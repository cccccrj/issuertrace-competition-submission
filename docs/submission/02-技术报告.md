# 技术报告：上市公司事件智识（IssuerTrace）

## 1 问题理解与目标

财经事件研判需要联合分析公司公告、媒体报道、转载和监管问询中的时间、措辞、数值及证据状态。系统围绕「发生什么、涉及谁、何时、依据是什么、如何推进复核」组织可追溯的研判结论。

环境、版本和数据对应关系见 [README环境表](../../README.md#立即访问)。本次材料修订沿用已归档测试证据；处理后的业务与评测数据全部交付，见[数据范围](处理后数据交付范围.md)。线上部署保持原样。

本原型以长鑫科技和药明康德为平台案例，以主办方独立评测语料辅助检验跨公司能力。模型判定与人工复核分层保存，四值核验清晰区分支持、部分支持、冲突与待补证状态，为复核提供可追溯的依据。

## 2 技术路线

采集保留版本与来源 → 正文解析与守门 → 事件／要素／原子主张抽取 → 检索证据与四值裁决 → 重复／传播／版本变化／事项／候选因果关系 → 风险分级 → 人工认领、上报、退回、归档 → 通知、导出与审计。

大模型负责结构化抽取和有依据的解释；规则承担输入边界、归一化、状态约束和可重复计算；检索把回答限制到具体证据。算法入口及参数见04，实际数据结构见03与字段清单。

## 3 系统架构

```text
外部公开源／授权评测数据
       ↓
collector（留存原始版本）→ processor（批量分析／离线评测）
       ↓                         ↓
 collector.sqlite3          benchmark.sqlite3
       ↓                         ↓
 FastAPI：分析只读查询 + 单独人工记录写入 + 会话／权限／审计
       ↓
 Vue3：事件、风险档案、证据定位、关系、复核、通知、评测
       ↘ 可选模型网关：有来源约束的研判助手
```

应用层以Python/Uvicorn承载API，Web接入层提供前端页面及API路由。负载测试采用独立目录、数据库和回环入口。运行包携带分析结论，平台业务查询支持CPU部署，GPU用于可选的离线向量计算。

## 4 核心算法

事件抽取保留label_source与原文定位，引文通过原文跨度校验后落库；数值、币种、单位、期间分别处理。检索使用BM25，离线BGE-M3近邻作为主张裁决可选兜底。裁决输出SUPPORTED／PARTIAL／CONFLICT／UNVERIFIABLE，将证据不足与明确冲突分别记录。

重复聚类结合文本相似与传播证据组织事件关联。版本差异区分数字、修改、增加、删除，问询事项链关联问答与状态。候选因果关系保存证据、方向和来源，支持业务分析与进一步核实。风险机器分数与人工覆判分层存储，形成原始判断与复核结果的完整审计链。

## 5 关键模块与实现

| 模块 | 源码位置 | 职责 |
|---|---|---|
| 多源采集 | collector/、config/ | 来源配置、版本、请求记录、采集守门 |
| 分析与评测 | processor/ | 解析、抽取、检索、裁决、去重、关系与实验 |
| 分析查询 | api/db.py、api/routes/ | 只读连接、参数化SQL、分页与报告 |
| 人工复核 | api/review_db.py、api/dispatch_db.py | 人工任务、状态、角色边界、审计历史 |
| 会话与账号 | api/auth.py、api/users_db.py | 四角色、PBKDF2、签名Cookie、停用校验 |
| 研判助手 | api/assistant.py | 事件／风险范围、逐步检索、来源引用、降级 |
| 前端 | web/src/ | Vue交互、证据展示、双主题、业务流程 |

账号密码以PBKDF2-SHA256存储，240000迭代。业务API默认登录保护；只读viewer不能修改，analyst可提出结论，reviewer负责复核，admin管理账号。通知收件和已读状态按人隔离。Webhook采用allowlist并默认干运行，避免测试真正外发。

## 6 实验设计

算法质量与工程可靠性分别评价。前者记录数据切分、标签来源、基线、指标和适用范围；后者运行后端／前端单测、HTTP验收、真实浏览器、协同状态链、10路同时写入审计及50独立身份混合负载。10路写入采用同一分析师身份的独立Session，跨角色协同另由不同账号验证。业务压测覆盖真实通知已读写入，GPU计算与模型并发容量采用独立实验，分别体现各链路能力。

主办方公开验证集用于开发评测、阈值标定和少样本对照，各实验按数据用途分别记录。系统已建立300条人工复核队列，后续独立人工裁定与最终盲测按独立协议扩展，开发指标与人工评价各自保留清晰的数据来源。

## 7 效果评估

冻结数据规模和本次工程验收见05及机器证据。历史可核对实验：重复聚类pairwise precision 0.9959、F1 0.8569、B³ F1 0.9774；情绪macro-F1 0.6568，对照0.3048；事件类型micro-F1 0.4660，对照0.3333。实验设计、计分样本和基线对照统一见[测试报告](05-测试报告.md#算法质量评价)，历史结果由交付评测库中的运行台账追溯。

事项实验分别记录线上方案0.4211和少样本对照0.6497，便于分析不同配置的效果。固定启发式检索标签上，候选命中率由BM25的88.3%提升至Fallback的89.4%；典型16例用于展示案例流程。候选命中、案例验证与独立人工事实评价分别统计，指标面向系统能力评价与业务复核。

## 8 适用范围、不足分析与扩展路线

本次以两家公司验证多源采集、时间解析、主张核验与协同闭环，并通过来源留存、版本管理和原文定位支撑结果复查。规则与模型结果可在人工复核队列中对照；候选因果关系为后续专项识别实验提供可追溯输入。原生SQLite单进程方案实现轻量部署，已验证25用户交互延迟目标与50用户持续运行可靠性；多节点容量按专门协议扩展。模型网关配置及版本独立管理，授权原始附件可按数据说明接入，实现更广公司的采集复算与人工评估。

本轮已在独立4090D服务器完成固定93209段落／3922查询的3次BGE-M3 GPU编码与近邻计算，计时、吞吐、显存和平台回传结果见08及05报告。原编码实现、冻结输入和检索阈值保持一致；GPU数据与业务API延迟分别报告。更多batch、长度与严格同条件跨设备对比按04／07扩展。演示视频约3分14秒，与30页答辩PPT随V1.0交付，入口与摘要见[演示材料](演示材料.md)。
